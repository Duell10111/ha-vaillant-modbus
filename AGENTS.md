# AGENTS.md

## Scope

These instructions apply to the entire repository unless a more specific
`AGENTS.md` exists in a subdirectory.

## Project overview

This repository contains the `vaillant_modbus` Home Assistant custom
integration for the Vaillant Gateway eBUS/Modbus SV2. Production integration
code lives in `custom_components/vaillant_modbus/`, and tests live in `tests/`.
The supported runtime is Python 3.13 or newer.

`vpn_container/` provides the VPN path used to reach the remote Modbus TCP
gateway. Its Compose stack runs Gluetun with a custom OpenVPN configuration and
an Alpine sidecar that shares Gluetun's network namespace. The sidecar listens
on TCP port 5020 and forwards the byte stream unchanged to `10.3.0.1:5020`.

`vpn_container/` contains or references sensitive VPN material. Never open,
print, copy, edit, or commit private keys, certificates, credentials, or the
contents of `.ovpn` files unless the user explicitly requests work on the
specific file. In particular, do not inspect untracked `*.key` or `*.crt` files
merely to understand the repository.

## Working practices

- Inspect `git status` before editing. Preserve all user changes and do not
  modify unrelated files.
- Use `rg` or `rg --files` for repository searches. Exclude virtual
  environments, caches, generated bytecode, and secret-bearing directories.
- Keep changes narrowly scoped. Do not refactor unrelated code while fixing a
  bug or adding a feature.
- Follow the existing Python style: type annotations, concise docstrings,
  immutable definitions where practical, asynchronous Home Assistant APIs,
  88-character lines, and double quotes.
- Add or update tests for every behavior change. Prefer focused tests first,
  followed by the complete verification suite.
- Do not access live heating equipment during automated tests. Use the existing
  in-memory/mock unit abstractions.
- Do not add dependencies unless they are necessary. Update `pyproject.toml`
  and relevant documentation together when a dependency changes.
- Do not manually bump release versions unless the task explicitly asks for a
  release; Release Please synchronizes project and manifest versions.

## Home Assistant architecture

- The integration must borrow a Home Assistant-owned Modbus connection through
  `modbus_api.py`. It must never create, reconnect, or close an independent TCP,
  UDP, or serial transport.
- Keep I/O centralized in `VaillantCoordinator`; entities should expose
  coordinator state and delegate writes rather than communicate with Modbus
  directly.
- Preserve async behavior. Never block the Home Assistant event loop with
  synchronous network or filesystem work.
- Maintain correct config-entry setup, reload, and unload behavior. Any
  listener or callback registered during setup must be removed on unload.
- Diagnostics must redact connection identifiers, network addresses,
  credentials, and other transport details.
- User-visible strings must use translation keys. Keep `strings.json` and all
  files under `translations/` consistent when adding or changing UI text.

## Modbus and heating-safety invariants

The supplied `01_Modbus_Handbuch_V120.pdf` is the authoritative source for
register addresses and semantics. Do not guess register metadata. If the manual
does not establish an address, type, scale, range, access mode, or byte/word
order, stop and request clarification.

- Never read or write reserved register `0`.
- Never read more than `MAX_REGISTERS_PER_REQUEST` (currently 16) registers in
  one request.
- Use holding-register reads (function `0x03`) and single-register writes
  (function `0x06`) as documented by this project.
- Preserve the minimum request spacing enforced by the shared unit handle.
- Decode signed 16-bit values with two's complement and preserve the documented
  big-endian register order for 32-bit and 64-bit values.
- Only definitions explicitly documented as writable may be exposed for
  writing. All writes must pass through the central `encode_register` path.
- Enforce documented minimum, maximum, step, enum, width, and data-type
  constraints before issuing a write. Reject read-only and multi-register
  writes through the normal entity write path.
- Registers `600` through `613` are intentionally unsupported because time
  programs require a complete transactional busy/queue/synchronization
  workflow. Do not expose them as independent entities.
- Optional hardware must be detected conservatively. Missing optional blocks
  should not make the whole integration unavailable, and all-zero placeholder
  data is not proof that hardware exists.
- Never create an automated test that writes to a real or production heating
  system. Live write verification, when explicitly requested, must use one
  documented low-risk parameter and remain under direct user control.

When changing the register map, update the relevant definition, poll block,
entity behavior, translations, README register table, and tests together.
`tests/test_register.py` must continue to cover signed/scaled/wide decoding,
safe encoding, boundary rejection, enum validation, read-only rejection, the
16-register request limit, and the reserved-register invariant.

## VPN container architecture and invariants

For changes under `vpn_container/`:

- `docker-compose.yml` uses `qmcgaw/gluetun` as a custom OpenVPN client. Gluetun
  owns the VPN network namespace, firewall, routes, and the published host port
  `5020/tcp`. Keep `NET_ADMIN` limited to this service; do not add
  `privileged: true`.
- `modbus-forwarder` uses `network_mode: "service:gluetun"`. It therefore has no
  independent interfaces or IP address and reaches the remote gateway through
  Gluetun's routes and firewall.
- `modbus-forwarder.sh` is deliberately a transparent TCP relay. Its standard
  input and output are connected to an incoming socket by BusyBox `nc`, and it
  opens the upstream connection to `10.3.0.1:5020`. Do not add register
  decoding, polling, writes, protocol transformations, or Python dependencies
  to this forwarding path.
- Port `5020` is intentionally published because this architecture exposes the
  local relay. Treat any change to its host binding or firewall allowance as a
  security-sensitive change. Do not expose additional ports without an
  explicit requirement.
- Preserve Gluetun's firewall as the VPN kill-switch. Do not add bypass routes,
  broad outbound subnets, permissive post-rules, or fallback paths that could
  send remote-gateway traffic outside the VPN.
- Keep the custom OpenVPN configuration and its CA, client certificate, and
  private key as runtime mounts. When editing Compose, keep these mounts
  read-only and never bake them into an image or reproduce their contents in
  documentation, fixtures, logs, or command output.
- `FIREWALL_INPUT_PORTS` must include only ports intentionally served from the
  shared namespace. `FIREWALL_OUTBOUND_SUBNETS` is for explicitly allowed
  non-VPN subnets; do not confuse it with the remote subnet routed through the
  VPN.
- `iptables/post-rules.txt` currently documents that no custom post-rules are
  needed. Add rules only when Gluetun's supported firewall settings cannot
  express a verified requirement, and keep any rule narrowly scoped.
- `connect_vpn.sh` is a host-side convenience script that invokes OpenVPN with
  `sudo`; it is not part of the Compose data path. Never execute it
  automatically, because doing so changes host networking and initiates an
  external VPN connection.
- `modbus_test.py` is a separate, manual, read-only diagnostic client. It may
  read documented register blocks in batches of at most 16, but it must not be
  executed against live equipment without explicit user authorization. Do not
  import it into the Home Assistant integration or the TCP-forwarder container.

## Verification

Use the project virtual environment when available:

```bash
. .venv/bin/activate
pytest
ruff check .
ruff format --check .
python -m compileall custom_components/vaillant_modbus
```

For a focused register change, run at least:

```bash
pytest tests/test_register.py
```

For VPN container changes, run only credential-free static checks by default:

```bash
bash -n vpn_container/connect_vpn.sh
sh -n vpn_container/modbus-forwarder.sh
docker compose -f vpn_container/docker-compose.yml config --quiet
python -m compileall vpn_container/modbus_test.py
```

Do not run `connect_vpn.sh`, `docker compose up`, the TCP relay, or
`modbus_test.py` as routine verification. These commands can connect to
external systems, alter networking, expose a host port, or query live heating
equipment. Do not claim end-to-end VPN, forwarding, or device verification
unless it actually occurred with explicit authorization. Report which checks
ran and which checks could not run.

## Documentation expectations

Update `README.md` and/or `DEVELOPMENT.md` when setup, supported behavior,
safety constraints, dependencies, or operator commands change. Keep examples
free of real addresses, usernames, passwords, certificates, and keys. Clearly
distinguish a TCP reachability check from a Modbus protocol test.
